## 三、关键决策与理由

### 3.1 为什么先做规则层，而不是先做 FastAPI

V3.0 把"前后端分离"排在第一位，理由是"多用户并发"。但：
- Streamlit 每会话独立，并发本来不是瓶颈；
- 真正的瓶颈是 SQLite 写锁，而运行时几乎全 `SELECT`，已是事实读写分离；
- 立项书的六项指标没有一条需要 FastAPI。

所以顺序反过来：**先让判定可证明，再谈架构解耦**。FastAPI 降级为 P3 可选项。

### 3.2 为什么规则要外置成 CSV 而不是写死在 Python

三个直接收益：
- 导师改规则不用改代码，也不怕改坏逻辑；
- 每次载入都全量重建 `Rules` 表，天然幂等；
- 规则带 `source_ref` 与 `version`，"可追溯"才有落点。

代价：规则合法性需要校验（`schema.py` 会检查 action 只能是禁/慎/宜、tag 必须已定义）。

### 3.3 为什么"禁/慎/宜"三档而不是二元

二元会逼出两个错误：要么把"温补偏油"一刀切禁掉（气虚者其实可少量），要么全部放行。三档让"黄焖鸡米饭"这类菜能表达为"气虚慎、湿热禁"，这也是体质敏感度从 0 变成 9 的来源。

### 3.4 为什么 AI 输出要做后校验

"大模型只解释不判定"是写在立项书里的承诺，但**靠 system prompt 约束不是承诺，是请求**。加了 `validate_ai_text`：出现穴位/剂量/处方词、出现与"禁"冲突的表述、出现未放行菜名，一律丢弃 AI 文本并降级为本地解释。这是把承诺变成代码。
