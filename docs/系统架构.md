# 知源智膳 · 系统架构

> 版本：规则 1.1.0 / 标签 1.1.0 / Schema 3　｜　更新：2026-11-18

## 一、一句话定位

**判定与表达分离**的本地优先食养辅助系统：菜品文本先被归一到属性标签，再由数据库里的规则给出"禁 / 慎 / 宜"的确定性结论；大模型只在结论已定之后负责把理由说成人话，且必须通过输出校验。

## 二、分层结构

```
┌──────────────────────────────────────────────────────────────┐
│ ① 展示层  app.py（Streamlit，290 行）                          │
│    方案生成 / 单菜查询 / 规则与合规 三个 Tab                    │
│    每条结果展示：判定档位 + 规则编号 + 出处 + 免责声明           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只传结构化参数（体质下拉、忌口多选）
┌───────────────────────────▼──────────────────────────────────┐
│ ② 编排层  shafe_mvp.py（396 行）· 唯一对外服务入口               │
│    generate_diet_plan() / check_food()                        │
│    ├─ 调判定层，拿结论与证据                                    │
│    ├─ [可选] 调 LLM 解释                                       │
│    ├─ validate_ai_text() 输出校验，不通过 → 丢弃并降级           │
│    └─ 15s 超时，任何异常都不阻塞本地结果                        │
└───────────────────────────┬──────────────────────────────────┘
```

## 三、一次请求的完整链路

```
用户填体质/情志/忌口
   │
   ▼
shafe_mvp.generate_diet_plan()
   │
   ├─ rule_engine.load_rules(体质) ────────► Rules 表（19 条，已审核）
   │
   ├─ 取 kind='dish' 全量菜品（203 道）
   │     └─ 逐条 evaluate()
   │           ├─ Dish_Tag（635 条）→ 命中的标签
   │           ├─ 标签 × 规则 → 动作（禁/慎/宜）
   │           └─ 产出 Evidence{rule_id, action, tag, rationale, source_ref, version}
   │
   ├─ 用户忌口过滤 ────────────────────────► Constraint_Rule（173 条）
   │
   ├─ 排序：宜 > 慎；情志匹配优先；证据少者靠前
   │
   ├─ [可选] LLM 解释
   │     └─ validate_ai_text()：违禁医疗词 / 与「禁」冲突 / 未放行菜名 → 拒绝
   │
   └─ 返回 {recommendations, blocked_details, rule_version, …}
         │
         ▼
   app.py 渲染卡片 + 导出 TXT（含规则依据与免责声明）
```

单菜查询走另一条入口 `check_food()`：

```
口语输入 → 直判词（"甜的"/"炸的"）→ search_dish
   ├─ 精确名 → 命中
   ├─ 别名表（Dish_Alias 27 条）→ 命中
   ├─ 子串（单字返回候选；反向包含要求菜名 ≥3 字）
   └─ 未收录 → 明确返回"未收录"，不猜
        │
        ▼
   evaluate() → 禁/慎/宜 + 证据 → [可选] AI 解释
```

## 四、数据模型

| 表 | 行数 | 作用 |
|---|---|---|
| `Dish` | 320 | 菜品 203（`kind=dish`）+ 基础食材 117（`kind=ingredient`） |
| `Canteen` | 318 | 档口与价格，一条菜多档口 = 多行 |
| `Dish_Tag` | 635 | 派生标签，带 evidence 与 tag_version |
| `Dish_Source` | 320 | 溯源五列：来源类型/说明/采集人/日期/校区 |
| `Rules` | 19 | 体质规则，禁/慎/宜 + 依据 + 出处 + 审核状态 |
| `Rule_Review` | 19 | 规则审核日志（无外键，只增不改） |
| `Dish_Review` | 20 | 菜品性味审核日志（同上） |
| `Dish_Alias` | 27 | 口语别名 → 标准菜名 |
| `Constraint_Rule` | 173 | 素食/无麸质/不吃辣/不吃苦味 |
| `Emotion_Rule` | 322 | 情志偏好（只影响排序，不影响判定） |
| `schema_migrations` | — | 迁移记录（版本、时间、明细） |

**三种 `kind` 语义**：`dish` 进推荐方案；`ingredient` 只可查询。不区分会导致"今日推荐：生姜"。

## 五、三个分离（架构的核心主张）

1. **判定 / 表达分离**：能不能吃由 SQLite 规则决定；LLM 只解释。LLM 的输入白名单只有"库内解析的菜名 + 下拉框体质 + 引擎产出的规则编号与依据"，**用户自由文本从不进入 prompt**。
2. **规则 / 代码分离**：规则写在 `rules.csv`，改规则不改 Python；载入时校验动作合法、标签已定义、出处非空。
3. **数据 / 代码分离**：`food.csv` / `rules.csv` / `aliases.csv` 是唯一真源，`food.db` 可由 `python init_db.py` 完整重建。

## 六、证据链（为什么说"可证明"）

| 机制 | 命令 | 证明什么 |
|---|---|---|
| 验收门禁 | `python tools.py gate` | 单测 43 条 + 六项指标 + 数据完整性，任一不过返回非零，可挂 pre-commit |
| 指标评测 | `python eval_metrics.py` | 准确率、敏感度、违规率、可追溯率、延迟、免责声明 |
| 金标 | `gold_labels.json`（99 条） | 人工/文献标注，外置可审，不写死在代码里 |
| 规则变更影响 | `tools.py snapshot` + `resync` | 改规则后哪些菜翻盘、哪些金标需复核 |
| 审核留痕 | `tools.py review` / `data-review` | 规则与菜品分别记 `Rule_Review` / `Dish_Review` |
| 溯源 | `Dish_Source` + `docs/sources/` | 每条数据能回答"谁、何时、从哪、哪个校区" |

## 七、技术选型与取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 前端 | Streamlit | 单人项目，省掉前后端联调；会话独立，无需额外并发设计 |
| 存储 | SQLite + WAL | 数据量小、单机部署；WAL 让读写不互相阻塞 |
| 后端框架 | **不引入 FastAPI** | 六项考核指标没有一条需要它；可回退性优先。若将来做开放 API，只在其上包三个端点，`rule_engine` 不动 |
| 大模型 | OpenAI 兼容接口，BYOK | 密钥不落盘；平台不承担调用成本 |
| 体质覆盖 | 气虚 / 湿热 | 两种体质的饮食禁忌差异最明显，先做闭环再扩 |

## 九、已知边界

1. **标签层是最大误差源**：判定错先查 `Dish_Tag`，而不是先改规则。
2. **规则档位是按菜品设计的**，套到食材上偏严（羊肉、羊杂对气虚被一票否决）。
3. **只覆盖两种体质**，其余体质明确返回"暂不支持"，不猜。
4. **性味属教材级证据**，未逐条核对页码；热量为成分表参考值。
5. **发物档位待定**：湿热下虾蟹为"慎"，临床多建议避免，升"禁"需导师裁决。
