# 小程序是怎么做出来的

> 记录从"想做成小程序"到"能在开发者工具里跑"的完整过程，含判断、取舍与验证方式。

## 〇、一句话概括

**不写后端，把判定搬到手机里。** 321 道菜 + 19 条规则的判定逻辑用 JS 重写一遍，
数据打包进小程序包（104 KB），于是不需要服务器、域名、API Key，也不怕食堂没信号。

## 一、先算账：能不能零成本

做之前先确认三件事，任何一件不成立，方案就要改：

| 问题 | 结论 |
|---|---|
| 判定能不能离线？ | 能。规则引擎是纯函数，输入菜名+体质，输出判定 |
| 数据多大？ | 321 菜 + 19 规则 + 标签 ≈ 104 KB，主包上限 2 MB |
| 分享要钱吗？ | 不要。转发、朋友圈、小程序码都免费；认证 30 元/年可选 |

三个都过，才决定"纯本地方案"。

## 二、架构：三层

```
Python 侧（唯一真源）
  food.csv / rules.csv / constitution_quiz.py
        │  init_db.py
        ▼
  food.db
        │  export_miniprogram.py / export_quiz.py
        ▼
小程序侧（只读数据）
  data/db.js     菜品 + 标签 + 规则 + 忌口映射
  data/quiz.js   11 道自评题
  utils/engine.js  判定引擎（rule_engine.py 的移植）
  utils/quiz.js    自评计分（constitution_quiz.py 的移植）
  pages/         首页 · 自评 · 推荐 · 记录
```

关键约束：**小程序里不写业务数据**，全部由 Python 导出。否则两边会慢慢说不一样的话。

## 三、动手顺序（实际做的）

### 第 1 步：导出数据
写 `tools/export_miniprogram.py`，从 SQLite 读四张表，拼成一个 JSON：

- `Dish` + `Dish_Tag` → 每道菜的标签
- `Rules` → 19 条规则（按体质分组）
- `Constraint_Rule` → 忌口对应的菜品 ID（素食/不吃辣等）
- `Dish_Source` / `Canteen` → 校区与档口信息

同时导出 `db.js`（小程序不能 `require` JSON，只能 require JS）。

### 第 2 步：移植引擎
把 `rule_engine.py` 的 `evaluate` 与 `plan` 改写成 `utils/engine.js`：

- 判定：命中的规则里取最高档（禁 > 慎 > 宜），无命中按"宜"放行
- 方案：过滤忌口 → 剔除"禁" → 打乱 → 按 宜 > 慎 排序 → 取前三

**最容易错的不是逻辑，是随机性。** Python 的 `random.Random(seed)` 和 JS 的
`Math.random()` 不同，必须自己写一个线性同余生成器，才能保证同一条件下结果可复现。

### 第 3 步：对拍（这一步最重要）
把 Python 引擎对 **321 道菜 × 2 种体质 = 642 次判定**的结果导出成基准，
再用 Node 跑 JS 引擎逐条比对：

```
对拍 408 条，不一致 0
```

（408 = 其中 kind='dish' 的菜，食材类不参与推荐。）

**为什么必须做**：JS 和 Python 在字符串比较、排序稳定性、默认值处理上都有差异。
没有对拍，用户会看到"网页说禁、小程序说宜"，一票否决。

### 第 4 步：搭页面
四个页面，都用原生 WXML/WXSS：

| 页面 | 内容 |
|---|---|
| `index` | 选状态、忌口芯片、食堂范围、"开始自评"入口 |
| `quiz` | 11 题一题一屏、进度条、上一题/下一题、结果页 |
| `result` | 三道菜 + 判定徽章 + 可展开的规则依据 + 换一批 |
| `record` | 14 天打卡 + 三个徽章（连续/已记/今日） |

设计沿用网页版的令牌：暖白 `#FAF6EE`、草绿 `#5E7F52`、陶土橙 `#B9643F`，
卡片圆角 16rpx（8px），判定用"图标 + 文字 + 底色"三重编码。

### 第 5 步：自评题库同步
自评的 11 道题和计分公式定义在 `constitution_quiz.py`，导出成 `data/quiz.js`，
JS 侧 `utils/quiz.js` 复刻同一套公式：

```
转化分 = [(原始分 - 条目数) / (条目数 × 4)] × 100
```

用 6 组代表性作答对拍，分数与结论完全一致。

### 第 6 步：分享
三个页面实现 `onShareAppMessage`（转发好友/群），首页与推荐页实现
`onShareTimeline`（朋友圈，单页模式）。全部免费。

## 四、踩过的坑

| 坑 | 表现 | 解法 |
|---|---|---|
| JSON 不能 require | 编译报错 | 同时导出 `db.js` |
| 随机数不可复现 | 同一条件每次推荐不同 | 自写 LCG 生成器 |
| **WXML 不支持方法调用** | `selected.indexOf(item)` 恒为 undefined，芯片永远不高亮 | 在 JS 里预先算好 `{name, on}` 列表 |
| **onLoad 只跑一次** | 从自评页返回，首页芯片不更新 | 用 `onShow` 重新读全局状态 |
| **编码后再比较** | `encodeURIComponent('全部')` 不等于 `'全部'`，被当成校区名，筛出空结果 | 先 `decodeURIComponent` 再判断 |
| PowerShell 写文件 | here-string 吃掉反引号和换行，JS 被写成乱码 | 改用编辑器写文件 |
| 导出脚本路径 | `Copy-Item -Recurse` 把目录内容摊平到父目录 | 用 robocopy /MIR |
| 中文路径 | git 输出转义，Node 读不到 | `core.quotepath=false` + `-z` |

## 五、上线还要做什么

代码能跑 ≠ 能发布。剩下的是流程，不是技术：

1. **注册小程序**（个人主体，免费）
2. **小程序备案**（免费，1–20 个工作日，期间可继续改代码）
3. **类目选「工具」**，不要选医疗健康——否则要《医疗机构执业许可证》等资质
4. 开发者工具上传 → 提交审核（1–3 天）→ 发布

**文案红线**：小程序里不出现"体质辨识、调理、诊断、疗效"，否则按医疗类判。
内部规则表叫"禁/慎/宜"没关系，界面上一律显示"推荐/适量/暂不建议"。

## 六、数据更新怎么做

```
改 CSV → python init_db.py → python tools/export_miniprogram.py
       → python tools/export_quiz.py → node tools/parity_check.js
       → 开发者工具上传新版本 → 审核
```

对拍不过就不要发版。

## 七、已知取舍

| 取舍 | 代价 | 为什么接受 |
|---|---|---|
| 不用后端 | 反馈收集不到、记录不能跨设备 | 零成本、离线可用、无隐私风险 |
| 数据打包 | 更新要发版（1–3 天） | 菜品变化不快 |
| 本地模板解释 | 不如 LLM 自然 | 快、免费、不会说错 |
| 只支持两种体质 | 覆盖有限 | 规则与金标只做到这两种，不做虚的 |
