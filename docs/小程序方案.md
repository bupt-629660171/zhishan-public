# 小程序方案（零成本版）

> 目标：在**不花钱**的前提下，把"食堂现场选菜"做成手机上一按就用的东西。
> 结论：可以，而且不需要服务器、不需要域名、不需要 API Key。

## 一、为什么零成本可行

| 项 | 需要花什么 | 我们的做法 |
|---|---|---|
| 服务器 | 月租 | **不需要**——判定在手机本地跑 |
| 域名 + 备案 | 钱 + 2 周 | **不需要**——小程序不调外部接口 |
| 数据库 | 月租 | **不需要**——数据打包进小程序包 |
| API Key | 按次计费 | **不需要**——解释用本地模板 |
| 小程序认证 | 30 元/年 | **可选**，不认证也能发布 |
| 小程序备案 | 免费 | 必须做（1–20 个工作日） |

数据量：321 道菜 + 19 条规则 + 标签 ≈ **104 KB**，小程序主包上限 2 MB，绰绰有余。
额外好处：**食堂信号差也能用**，完全离线。

## 二、架构

```
小程序（WXML/WXSS/JS）
  ├─ data/db.js        321 道菜、标签、规则、忌口映射（构建时生成）
  ├─ data/quiz.js      11 道自评题（构建时生成，与 Python 同源）
  ├─ utils/engine.js   判定引擎（rule_engine.py 的 JS 移植）
  ├─ utils/quiz.js     自评计分（constitution_quiz.py 的 JS 移植）
  └─ pages/
      ├─ index    选状态 + 忌口 + 食堂范围
      ├─ quiz     11 题自评（一题一屏，带进度）
      ├─ result   三道推荐 + 规则依据 + 换一批
      └─ record   14 天打卡 + 连续记录徽章
```

Python 侧仍是唯一真源：改 `food.csv` / `rules.csv` → `init_db.py` → `tools/export_miniprogram.py` → 发版。

## 三、判定一致性怎么保证

把 Python 引擎对 321 道菜 × 2 种体质的判定导出成基准，再用 Node 跑 JS 引擎逐条比对：

```
对拍 408 条，不一致 0
```

**每次改规则或改引擎，都要重跑这个对拍**，否则小程序和网页会给不同答案。

## 四、上线步骤

1. **注册小程序**（mp.weixin.qq.com，个人主体，免费）
2. **小程序备案**（后台填资料 + 人脸核验，免费，1–20 工作日）
3. **微信开发者工具** → 导入 `miniprogram/` 目录（AppID 可先用测试号）
4. **类目选「工具」**（如"效率-信息查询"），**不要选医疗健康**
5. 上传 → 提交审核 → 发布

## 五、审核注意（决定能不能过）

微信会按**内容**判类目，文案里出现"体质辨识、调理、诊断、疗效"就可能被判医疗、要求资质。所以小程序内的用词必须是：

| 不要用 | 用 |
|---|---|
| 体质 | 状态 / 偏好 |
| 调理方案 | 今日推荐 |
| 宜 / 慎 / 禁 | 推荐 / 适量 / 暂不建议 |
| 中医食养 | 食堂选菜参考 |
| 自评问卷 | 偏好设置 |

界面已按此口径写；改文案时守住这条线。

## 六、数据更新流程

```powershell
# 1) 改数据（唯一真源是 CSV）
# 2) 重建库
python init_db.py
# 3) 导出小程序数据与题库
python tools/export_miniprogram.py
python tools/export_quiz.py
# 4) 对拍（必须 0 不一致）
node tools/parity_check.js
# 5) 微信开发者工具上传新版本
```

## 七、后续要不要上后端

| 需求 | 是否需要后端 |
|---|---|
| 换一批、看推荐、记录打卡 | 不需要（现在就能） |
| 收集用户反馈、多端同步 | 需要（微信云开发有免费额度，但发布后 15 天到期） |
| 多人协作维护规则 | 不需要（规则在仓库里，改完发版） |

结论：**先不上后端**。等有人真的用、真的愿意反馈，再考虑云开发。

## 八、已知限制

- 数据更新要发版（审核 1–3 天），不适合高频改动；
- 没有账号体系，记录只在本机；
- 解释是本地模板，不如 LLM 自然（但更快、零成本、不会说错）；
- 小程序包体积会随菜品增长，超过 2 MB 需要分包。
