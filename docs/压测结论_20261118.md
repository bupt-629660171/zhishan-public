## 关于那条 115 秒的"最大延迟"

报告里 `max = 115,173 ms` 看着吓人，但它**不是代码问题**。系统事件日志显示：

```
19:10:17  系统正在进入新型待机（Modern Standby，事件 506）
19:12:24  系统正在退出新型待机（事件 507）
```

压测进行到第 21 分钟时，机器自动进入待机约 **2 分 07 秒**。那一次请求的 `time.perf_counter()`
把睡眠时间也算了进去，于是记录成 115 秒。

佐证：均值 23.1ms，与 p50 22.4ms 几乎重合——如果代码真有卡顿，均值会被明显拉高。
31 万次请求里只有这 1 次超过 5 秒。

**已改进脚本**：现在会把 >5 秒的请求单独列出（耗时、操作、发生时间），并在报告里提示
「疑似系统待机/杀毒扫描」，下次不用再靠事件日志反推。

## 内存 +15.4 MB 怎么判断

30 分钟 +15.4 MB，约 0.5 MB/分钟。这个量级**不足以判定泄漏**：
Python 的内存池、SQLite 页缓存、字符串驻留都会在前期爬升后趋于平稳。真正的泄漏特征是
「持续线性上涨、不回落」。本次只采了首尾两点，看不出曲线。

**下次压测建议**：开着任务管理器看内存曲线，或让我加一个每分钟采样的序列（脚本里已有心跳，加一行即可）。
