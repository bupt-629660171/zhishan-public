# 半开放更新链路（P3）

立项书承诺的「新增来源 → 抽取 → 审核 → 入库」闭环，最小实现如下。

## 为什么不能"用户改了就生效"

食养结论一旦被随意改动，整个"可追溯"就废了。所以入口是**候选池**，不是数据库：

```
用户反馈 → Candidate（待审） → 人工审核 → 采纳才写入 food.csv → init_db → 门禁
                    │
                    └─ 驳回：保留记录与理由，便于复盘
```

**候选池只存"建议"，不碰 `food.csv`**。这一步是整条链路的保险丝。

## 四步操作

### 1. 反馈（网页）

「✍️ 反馈纠错」Tab → 填菜名、类型（修正/补录）、建议性味与依据 → 提交。
写入 `Candidate(status=待审)`，`submitted_by` 记为匿名。

### 2. 查看候选

```powershell
python tools.py candidate list
#   #1 [待审] 菌菇豆腐汤（new） by 演示用户 2026-11-18T17:52 试运行：演示半开放链路
```

### 3. 审核

```powershell
python tools.py candidate approve 1 --reviewer 项目负责人 --reason "补录通用菜，依据合理"
# 或
python tools.py candidate reject 1 --reason "性味与当地做法不符"
```

采纳时会做三件事：
1. 追加/修正 `food.csv`（`source_type=用户反馈`、`source_ref=候选 #id`）；
2. 状态改为「已采纳」，记审核人与时间；
3. 写一条 `Dish_Review`，与人工审核共用同一本审计账。

若菜名已存在却按"新菜"提交、或按"修正"提交了不存在的菜，会直接报错拒绝。

### 4. 生效与验收

```powershell
python init_db.py
python tools.py gate
```

## 状态机

| 状态 | 含义 | 可否再处理 |
|---|---|---|
| 待审 | 新提交 | 可采纳/驳回 |
| 已采纳 | 已写入 food.csv | 否 |
| 已驳回 | 保留理由 | 否 |

## 已知边界

1. **没有自动抽取**：候选由人填写，不做 LLM 抽取。姿态保守，但可控。
2. **无身份体系**：`submitted_by` 固定匿名，无法防刷。公开部署前需要加限流或简单校验。
3. **审核是命令行**：单用户够用；多人协作时要做一个审核页（P4 可做）。
4. **不自动重算指标**：采纳后必须重跑 `eval_metrics.py`，确认没把金标打穿。
