# V3.0 商品化计划书评估与架构精进建议

评估对象：《知源智膳_商品化工程与架构演进计划书_V3.0》
评估时间：2026-11-15
评估依据：当前仓库实际实现（`rule_engine.py` / `tags.py` / `rules.csv` / `eval_metrics.py`）与实测数据

---

## 〇、一句话结论

V3.0 的**商业叙事是完整且可信的**，三阶段路线也基本可执行；但它把工程重心押在了"前后端分离"和"语义理解"上，而这两件事**对结题指标没有贡献**。它真正缺的是四样东西：**规则治理、评测门禁、数据溯源、隐私边界**。建议"采纳其商业化框架、重排其工程优先级"。

| 2 | 代码与数据解耦，标准 CSV 模板 | 已做：`rules.csv`/`aliases.csv`/`food.csv` 为唯一真源，`tools.py import` 校验后合并 | ✅ 采纳，已完成 |
| 3 | 前端加反馈入口，收集纠错 | 未做 | ✅ 采纳，但**必须接进规则审核链**，见下 |
| 4 | 云端部署，生成公网链接 | 未做 | ✅ 采纳，但只做**只读公开实例**，见下 |
| 5 | 自动化测试覆盖拦截/降级场景 | 部分：已有 26 条单测，缺 AI 超时与无 Key 降级 | ✅ 采纳，补 4~6 条即可 |

其中第 3 条最值得展开：V3.0 想的是"踩/赞按钮"，这是**产品思路**；你真正需要的是**治理思路**——反馈进来后要能走完"候选 → 待审 → 已发布"的链路。这条链路是你立项书里"半开放知识库更新机制"的承诺，也是结题演示的压轴戏。所以反馈表不要设计成 `like/dislike`，要设计成：

```
Feedback(id, dish_id, field, old_value, new_value, reason, reporter, campus, created_at, status)
```

`status` 走 `待审 → 采纳 / 驳回`，采纳后写回 `food.csv` 并升 `TAG_VERSION`。这样"用户纠错"直接变成"知识库演进"，答辩时是一个完整闭环。

## 二、建议改做的（5 条）

### 2.1 FastAPI：不是不能做，是"现在做收益最低"

V3.0 给出的理由是"让代码具备多用户并发访问的能力"。这个判断**对错了瓶颈**：

- Streamlit 本身是每会话独立进程内状态，**并发访问不是瓶颈**；
- 真正的瓶颈是 **SQLite 写锁**（当前 `journal_mode=delete`，非 WAL）。而应用运行时几乎全是 `SELECT`，写只发生在 `init_db.py` 这类离线脚本里——**你现在的架构已经是事实上的"读写分离"了**。

也就是说：阶段一第 1 条（FastAPI）和第 4 条（读写分离）**解决的是同一个不存在的问题**。

**建议**：把 FastAPI 从"阶段一必做"降级为"阶段三可选"。如果要做，做成**薄 API**，三件事：

```
GET  /plan?constitution=&constraints=     → 调 rule_engine.plan()
GET  /dish?name=&constitution=            → 调 rule_engine.query_by_dish()
POST /feedback                            → 写 Feedback 表
```

`rule_engine.py` 一行不改。这样即使 FastAPI 做不完，把 API 层删掉也不影响主系统——**可回退**是单人项目的生命线。

### 2.2 jieba 解决不了你真正的痛

V3.0 说"引入 jieba 分词，解决输入'香锅'匹配'麻辣香锅'"。这不是分词问题，是**别名映射 + 歧义消解**问题。jieba 把"香锅"切成一个词，也不会自动知道它对应哪道菜。

这个问题已经解决了，而且可现场演示：

- `aliases.csv` 表驱动（香锅→麻辣香锅、黄焖鸡→黄焖鸡米饭、拉面→未收录）；
- 单字查询不再瞎匹配，返回候选让用户确认（查"肉"→ 8 个候选）；
- 未收录明确返回"未收录"，不猜。

**建议**：jieba 最多作为**召回补充**（用户输入"想吃不辣的鸡肉"这类长句时切词），且必须配置信度阈值，低于阈值就走"你说的是哪道？"而不是硬匹配。不要把它当成主检索方案。

### 2.3 多维度调养报告：穴位建议必须砍掉

V3.0 想把 Prompt 升级成【饮食匹配】【风险提示】【起居建议（如穴位建议）】。**前两项可以，第三项必须拒绝**，理由是你自己的核心卖点：

> "健康类产品容错率为 0，大模型只做翻译官，不做裁判员。"

穴位建议是**不可审计、无出处、不可复现**的医学建议。让 LLM 生成它，等于在系统里开了一个绕过规则引擎的后门——用户看到"按揉足三里"，而这句没有任何规则表支撑。评委只要问一句"这条穴位建议出自哪张表"，整个"零幻觉"叙事就塌了。

**建议**：起居建议做成**表驱动**，和 `rules.csv` 同构：

```
Lifestyle_Rule(id, constitution, category, advice, source_ref, status, version)
```

只放"少熬夜""饭后散步 20 分钟""晨起温水"这类生活常识级建议，每条带出处（如《中医体质学》调养原则）。穴位、剂量、药品名一律禁止出现在任何输出里——这条要写进 `EXPLAIN_SYSTEM_PROMPT` 的硬约束，并在输出后做正则校验。

### 2.4 读写分离与反馈机制自相矛盾

阶段一说"应用运行时只读，增删改全部剥离到 CLI"，阶段二又要"前端加反馈入口"。**只读运行时收不了反馈。**

**建议**：不要做重量级读写分离，改用更轻的两招：

1. `PRAGMA journal_mode=WAL` + `busy_timeout`，让读不阻塞写；
2. 反馈走 **append-only outbox**：前端把反馈写进 `feedback_outbox.jsonl`（追加写，无需事务），离线脚本 `tools.py feedback --ingest` 再合并进库。

这样并发、审计、可回退三件事同时满足，代码量不到 FastAPI 方案的 1/10。

### 2.5 限次付费解锁：删掉

学生项目接支付是合规与运营黑洞（主体资质、退款、对账、发票）。而且你的 BYOK 机制已经让边际成本归零，**没有付费的必要性**。V3.0 自己也写了"视未来运营成本而定"，那就明确写成"本期不做"。

## 三、三处事实性问题（会被导师或评委抓住）

这三条不是观点分歧，是**文档与事实不符**，建议直接改：

1. **"核心 MVP（前端 + 后端 + 数据库）已 100% 跑通"** 与阶段一"重构为 FastAPI 后端"矛盾。现在没有独立后端，`shafe_mvp.py` 是服务层。建议改为"前端 + 规则引擎 + 数据库已跑通，服务层尚未独立"。

2. **"本地硬拦截过滤掉 90% 的高频查询"** 无出处。实测：102 道菜中 **56 道被规则拦截（54.9%）**，且方案生成全程 **0 次 LLM 调用**。建议换成可复现的表述："在一次完整方案生成中，本地规则完成全部判定，LLM 调用次数为 0"。

3. **"Pydantic 防止恶意 Prompt 注入"** 在**当前架构下不成立**。我核实过：送给 LLM 的 prompt 只包含数据库解析后的菜名、下拉框选择的体质、规则引擎产出的 `rule_id` 与依据，**用户自由文本从不进入 prompt**——注入在结构上不可能发生。真正的风险是**将来加聊天入口时**破坏这个性质。建议把这条改写为"保持 LLM 输入白名单：只允许结构化字段进入 prompt，禁止透传用户自由文本"。

## 四、V3.0 的四个空白（架构上的真问题）

### 4.1 规则治理：审核结果必须落库（最高优先级）

V3.0 全篇没有"规则怎么被审、怎么被改、改了影响什么"的任何设计。而这是你当前架构的**唯一软肋**：现在的可追溯只到"这条推荐引用了哪条规则"，但**规则本身的可信度没有任何记录**。

本次已修复：19 条规则状态由"草案"转为"已审核"，审阅人：指导教师，审核时间 2026-11-15，`Rule_Review` 表留痕 19 条，规则版本升到 **1.1.0**；并用快照对比证明**审核前后判定翻盘 0 条**。

修复过程中还暴露了一个真 bug：`Rule_Review` 原本外键引用 `Rules(code)`，导致 `load_rules()` 全量重建规则时触发 `FOREIGN KEY constraint failed`。**审计日志必须独立于被审计对象**——这条经验值得写进结题报告。

### 4.2 规则变更影响分析

规则内容这次没变，但一旦扩到多校区、多人贡献，必然变。现在改一条规则，只能人工比对 102 道菜的判定。已补 `tools.py resync`：改完规则跑一次，直接输出"哪些菜翻盘、哪些金标需要复核"。这是"规则即数据"架构的必备配套，V3.0 完全没有。

### 4.3 标签层才是真正的误差来源

V3.0 把"语义理解"当成体验短板，但真正决定判定对错的是 `tags.py` 的关键词正则。**标签错 = 判定错**，而标签是隐式的、不可见的。

建议：把 `Dish_Tag` 的派生证据（命中了哪个词、出自哪个字段）做成可查看、可纠错的形式，纳入 `tools.py quality` 报告；扩到多校区时，允许数据贡献者修正标签——这比优化搜索框重要一个数量级。

### 4.4 数据溯源与隐私：多校区和公开部署的前提

V3.0 的"标准 CSV 模板"没有溯源字段，多校区一铺开，"100% 可追溯"立刻破功。建议 `food.csv` 增列：

```
source_type   # 菜单照片 / 档口公示 / 官网 / 口述
source_ref    # 照片文件名或链接
collected_by  # 采集人
collected_at  # 采集日期
campus        # 校区
```

同时有一条 V3.0 完全没提的**合规红线**：体质问卷是**个人健康数据**。现在的实现只存在 `session_state`、不落盘，这是对的，但必须写成显式设计约束——"不持久化任何问卷作答与健康信息，不记录用户身份"，并写进 README 的合规边界。公开部署时这条比免责声明更重要。

## 五、架构精进路线（按 ROI 排序）

| 优先级 | 动作 | 解决什么 | 成本 |
|---|---|---|---|
| P0 | 规则治理闭环：审核留痕 + 版本 + `resync` 影响分析 | 规则可信度可证明 | 已完成 |
| P0 | 评测门禁：`eval_metrics.py` 不进则不许合并 | 防止指标悄悄回退 | 半天 |
| P1 | 数据溯源字段 + 标签纠错队列 | 多校区可扩展 | 1 天 |
| P1 | `WAL` + 反馈 outbox | 并发与反馈闭环 | 半天 |
| P2 | LLM 输出后校验（禁新菜名/禁反转判定/禁穴位剂量） | 防幻觉兜底 | 半天 |
| P2 | 只读公开实例（Streamlit Cloud） | 结题演示与传播 | 1 天 |
| P3 | 薄 FastAPI（可选，可回退） | 对外 API | 2~3 天 |

注意排序逻辑：**P0/P1 全是"让已有能力可证明、可扩展"，P2/P3 才是"加新东西"。** V3.0 的顺序恰好相反——先加东西，再补证明。
