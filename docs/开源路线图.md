# 开源路线图（30 天）

> 选择开源作为主的理由：数据能滚起来、合规成本最低、对一个单人学生项目来说，
> 「被使用」比「被付费」更容易先拿到。

## 一、开源卖的是什么

开源本身不赚钱，它换三样东西：

1. **多校区数据**——别人替你补数据，这是最难自己攒的资产；
2. **可信度**——代码与规则可审计，比任何宣传都有力；
3. **机会**——B 端试点、实习、合作，通常从"我用了你的项目"开始。

## 二、30 天计划

### 第 1 周：把仓库变成"能被人看懂"的仓库

- [x] LICENSE（MIT + 数据声明）
- [x] CONTRIBUTING（含"加一个校区"的最短路径）
- [x] Issue / PR 模板
- [x] GitHub Actions 跑 `gate`
- [ ] README 加两张预览图（桌面 / 移动）
- [ ] 补"为什么做这个"的一段话（比功能列表更能打动人）
- [ ] 清理历史里的临时脚本与个人路径

### 第 2 周：发布 v1.0.0 并让人看见

- [ ] 打 tag `v1.0.0`，写 Release Notes（数据规模、指标、压测结果）
- [ ] 部署一个只读 demo（Streamlit Cloud），README 放链接
- [ ] 发两篇介绍：一篇讲**判定可追溯**（技术），一篇讲**食堂怎么吃**（用户）
- [ ] 找 3 个外校同学，请他们按 CONTRIBUTING 加一个校区

### 第 3 周：把"贡献"这条路走通

- [ ] 观察第一批 PR / Issue，记录卡点
- [ ] 修文档里让人卡住的地方（通常是环境与路径）
- [ ] 给第一个外部贡献者写感谢（公开），形成示范
- [ ] 把"数据纠错 → 候选池 → 审核 → 入库"跑一遍真实案例

### 第 4 周：复盘与决策

| 指标 | 看什么 | 决策 |
|---|---|---|
| Star / Fork | 有没有人关注 | < 20 说明传播没做好 |
| 外部 Issue / PR | 有没有人真用 | 0 说明入口太难 |
| 校区数 | 数据是否在滚 | 仍是 1 个说明激励不足 |
| demo 访问 | 有没有人点 | 周访问 < 100 说明渠道不对 |

**决策点**：如果 4 周后有 ≥2 个外部校区、≥10 个 Issue，就继续做 B 端试点；
否则回到产品本身，别急着扩。

## 三、开源的三个坑（提前说）

1. **规则类 PR 会失控**——每个人都有自己的"中医常识"。对策：无出处不合并，争议挂 Issue 讨论，不辩论。
2. **数据质量参差**——外校数据可能填错。对策：`campus` 必填、`source_ref` 必填、`gate` 卡格式，审核时抽查。
3. **被当成医疗建议**——README 与界面必须显眼声明；这也是为什么展示口径从"禁/宜"改成"推荐/暂不建议"。

## 四、暂时不做

- 不做 SaaS 订阅（获客与合规都太重）
- 不做账号体系（开源阶段不需要，反而增加隐私负担）
- 不做移动 App（H5/小程序等有真实需求再说）

## 五、需要你亲自做的三件事

1. **注册 GitHub 仓库并推上去**（我无法代做）
2. **部署 demo**（需要你的账号）
3. **找 3 个外校同学试用**（机器替代不了）

其余（README、Release Notes、贡献指南、CI）已经备好。
